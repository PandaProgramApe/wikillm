## Java 后端工程师核心技术栈 - 面试知识图谱

### 概述

本文档旨在为Java后端工程师，特别是准备高级职位面试的开发者，提供一个系统化的核心知识要点总结。内容整合了 Java 基础、JVM、并发编程、数据库优化、主流框架原理以及分布式系统设计等关键领域，旨在帮助读者构建完整的知识体系，既“知其然”，也“知其所以然”。

### 1. Java 语言核心与进阶

本章节涵盖了Java开发者必须深入理解的核心概念，从**基本数据类型**到**高级特性**。

#### 1.1 基础扎实

-   **值传递 vs. 引用传递**：**Java只有值传递**。对于对象，传递的是**引用（内存地址）的副本**。因此，方法内可以修改对象状态（形参指向同一对象），但**永远不能**让形参引用一个新的对象。
-   **`==` vs. `equals()` vs. `hashCode()`**：
    -   `==`：比较**基本数据类型**的值或**引用类型**的内存地址。
    -   `equals()`：默认行为同`==`，但大多数类（如`String`、`Integer`）重写了此方法，用于比较**对象内容**。
    -   **`hashCode()`**：与`equals()`有严格约定。**重写`equals()`必须重写`hashCode()`**。`equals()`返回`true`，则`hashCode()`必须相同；`hashCode()`不同，则`equals()`一定为`false`。这保证了对象在`HashSet`、`HashMap`等散列集合中的正确行为。
-   **`String`、`StringBuilder`、`StringBuffer`**：
    -   `String`：**不可变**字符串，适用于少量字符串操作或常量。
    -   `StringBuilder`：**可变**字符串，**线程不安全**，但性能最高，推荐在单线程环境下使用。
    -   `StringBuffer`：**可变**字符串，**线程安全**（方法使用`synchronized`修饰），性能略低于`StringBuilder`。
-   **泛型与通配符**：
    -   **泛型**：提供编译时类型安全，消除强制类型转换。`List<String>` 保证了列表中元素都是`String`类型。
    -   **通配符 `?`**：用于表示未知类型。遵循 **PECS (Producer Extends, Consumer Super)** 原则。
        -   `<? extends T>`：**生产者**，只能从中读取`T`类型或其子类型。
        -   `<? super T>`：**消费者**，只能向其写入`T`类型或其父类型。

#### 1.2 进阶特性

-   **反射**：在运行时获取类的完整结构信息（如方法、字段、构造器）并动态调用。是Spring、MyBatis等框架的基石。需注意性能开销和安全问题。
-   **注解 (Annotation)**：一种元数据形式，为代码提供额外的信息。通过**反射**在运行时处理注解是许多框架的常见做法。
-   **动态代理**：在运行时动态创建代理类及其实例。**JDK动态代理**基于接口，而**CGLIB**基于继承。Spring AOP默认根据目标对象是否实现接口选择使用哪种代理。
-   **异常体系**：
    -   **`Throwable`**：所有异常的父类。
        -   **`Error`**：程序无法处理的严重问题，如`OutOfMemoryError`。通常不捕获。
        -   **`Exception`**：程序可以处理的异常。
            -   **检查型异常 (Checked Exception)**：编译时必须处理（`try-catch`或`throws`），如`IOException`。
            -   **非检查型异常 (Runtime Exception)**：运行时可能抛出，无需显式处理，如`NullPointerException`。通常由程序错误导致。

### 2. JVM 内存模型与性能调优

深入理解JVM是面试高级职位的关键。本章节聚焦于**内存区域划分**、**垃圾回收机制**和**性能监控工具**。

#### 2.1 运行时数据区域

-   **程序计数器**：线程私有，记录当前线程执行的字节码行号。**唯一不会出现`OutOfMemoryError`的区域**。
-   **Java虚拟机栈**：线程私有，描述Java方法执行的内存模型。每个方法调用对应一个**栈帧**的入栈和出栈。
-   **本地方法栈**：线程私有，为`native`方法服务。
-   **Java堆**：线程共享，JVM管理的内存中最大的一块。**存储对象实例**，是垃圾回收器管理的主要区域。分为**新生代**（Eden, Survivor0, Survivor1）和**老年代**。
-   **方法区**：线程共享，存储已被JVM加载的**类信息、常量、静态变量、即时编译器编译后的代码**等数据。JDK 8后，被**元空间 (Metaspace)** 取代，使用本地内存。

#### 2.2 垃圾回收 (GC)

-   **判定对象存活**：
    -   **引用计数法**：无法解决循环引用问题。现代JVM已不采用。
    -   **可达性分析**：从一组称为 **GC Roots** 的对象（如虚拟机栈引用的对象、静态属性引用的对象）开始，向下搜索。任何与`GC Roots`不可达的对象都被判定为可回收。
-   **垃圾回收算法**：
    -   **标记-清除**：有内存碎片问题。
    -   **复制**：无碎片，但浪费空间。主要用于**新生代**。
    -   **标记-整理**：无碎片，效率适中。主要用于**老年代**。
    -   **分代收集**：现代JVM的默认策略。根据对象存活时间将堆划分为不同区域（新生代、老年代），对不同区域使用不同算法。
-   **常见垃圾收集器**：
    -   **Serial**：单线程，暂停所有用户线程（Stop The World），适用于小内存应用。
    -   **Parallel Scavenge / Parallel Old**：多线程，高吞吐量，适用于后台计算。
    -   **CMS (Concurrent Mark Sweep)**：追求低停顿，但会产生内存碎片。以**标记-清除**算法实现。
    -   **G1 (Garbage-First)**：服务端默认收集器，将堆划分为多个Region，可预测停顿时间。兼具低延迟和高吞吐量。
-   **性能监控与调优**：
    -   **常用命令**：`jps` (查看Java进程)、`jstat` (监控GC和类加载)、`jmap` (生成Heap Dump)、`jstack` (查看线程堆栈)、`jcmd` (一个多功能的JVM诊断工具)。
    -   **`jstat`使用示例**：`jstat -gcutil <pid> <interval> <count>` 可以监控JVM各内存区域使用率、GC次数和耗时。

### 3. Java 并发编程

深入理解并发是解决性能瓶颈和构建高响应系统的基础。

#### 3.1 线程基础与锁

-   **`start()` vs `run()`**：**`start()`** 会启动一个新线程，并自动调用其`run()`方法，实现并发。**`run()`** 只是一个普通方法调用，在调用线程内顺序执行，不会开启新线程。
-   **`synchronized`关键字**：**隐式锁**，由JVM实现，保证**原子性**、**可见性**和**有序性**。锁的是**对象**，而非代码。在JDK 1.6后经过大量优化（锁升级），性能与`ReentrantLock`相当。
-   **`volatile`关键字**：保证变量的**可见性**（一个线程修改后，其他线程能立即看到）和**有序性**（禁止指令重排）。**不能保证原子性**。
-   **`ReentrantLock`**：**显式锁**，由`java.util.concurrent`包提供。功能更丰富，支持**公平锁**、**可中断的锁等待**、以及通过`Condition`实现**精确唤醒**。
-   **锁升级**：JDK 1.6对`synchronized`的优化，锁状态从**无锁 -> 偏向锁 -> 轻量级锁 -> 重量级锁**，不可逆，目的是在无竞争或低竞争时避免进入内核态。
-   **死锁**：两个或更多线程互相持有对方需要的资源。破坏死锁的四大必要条件（**互斥、请求与保持、不可剥夺、循环等待**）之一即可避免，例如**按固定顺序获取锁**。

#### 3.2 并发工具与框架

-   **线程池**：`ThreadPoolExecutor` 是核心。通过`Executors`工厂类可以创建各种预配置的线程池（如`newFixedThreadPool`, `newCachedThreadPool`）。合理配置核心参数（`corePoolSize`, `maximumPoolSize`, `workQueue`, `handler`）至关重要。
-   **`AQS (AbstractQueuedSynchronizer)`**：**JUC包的基石**。`ReentrantLock`、`Semaphore`、`CountDownLatch`等同步器都基于它实现。它通过一个`volatile`的`state`变量和一个**CLH双向队列**来管理同步状态和等待线程。
-   **`ThreadLocal`**：提供线程局部变量。每个线程独立维护一个变量副本，实现**线程间数据隔离**。常用于存储用户会话、数据库连接等。需注意**内存泄漏**风险（键为弱引用，值为强引用，线程存活时值无法回收）。
-   **`CountDownLatch` vs `CyclicBarrier` vs `Semaphore`**：
    -   `CountDownLatch`：**一等多**，计数器不可重置。
    -   `CyclicBarrier`：**多等多**，计数器可重置，所有线程到达**屏障点**后可触发一个可选操作。
    -   `Semaphore`：**信号量**，控制同时访问某资源的线程数量。

### 4. 数据库：MySQL 优化与设计

数据库性能优化是后端工程师的核心技能之一，需从**SQL优化**、**索引**、**表设计**和**架构**等多个维度展开。

-   **存储引擎**：
    -   **MyISAM**：**读锁**、不支持事务、外键、崩溃恢复。适合**读多写少**的应用。
    -   **InnoDB**：**行锁**、支持事务（ACID）、外键、崩溃后安全恢复。**MySQL 5.5后的默认引擎**，对大多数应用是首选。
-   **索引优化**：
    -   **B+树索引**：最常用，支持等值和范围查询。
    -   **哈希索引**：仅支持等值匹配，检索速度极快，但无法排序。
    -   **联合索引**：遵循**最左匹配原则**。将区分度最高、最常查询的列放在最左边。
    -   **覆盖索引**：索引中**包含了查询所需的所有字段**，可以避免**回表**，是性能优化的重要手段。
    -   **索引设计原则**：避免在`NULL`值、值分布稀疏（如性别）的列上建索引；使用**前缀索引**优化大文本字段；**控制索引数量**（单表不超过5个，单索引字段不超过5个）。
-   **SQL与表设计优化**：
    -   **避免使用`SELECT *`**：只查询需要的字段，减少I/O和网络传输。
    -   **数据类型选择**：遵循**最小化**原则。能用`tinyint`不用`int`，能用`int`不用`char`。金额使用`decimal`或`bigint`（以“分”为单位），**禁止**使用`float`/`double`以避免精度丢失。
    -   **字段属性**：尽量设置为 **`NOT NULL`** 并指定默认值，能简化查询、节省空间、提升索引效率。
    -   **慢查询日志**：记录执行时间过长的SQL，作为性能分析的基础。可通过`mysqldumpslow`等工具分析日志。
-   **MySQL 锁机制**：
    -   **悲观锁**：`SELECT ... FOR UPDATE`，对数据行加**排他锁**，直到事务结束。适合写冲突频繁的场景。
    -   **乐观锁**：通过版本号 (`version`) 字段实现。更新时检查`version`，若被修改则失败重试。适合读多写少的场景。

### 5. 主流框架：Spring 生态

Spring框架是Java生态系统中的核心，其**IOC**和**AOP**思想是理解其所有组件的基础。

-   **Spring IoC (控制反转) / DI (依赖注入)**：Spring容器负责创建和管理对象（Bean）的生命周期及其依赖关系。通过与`@Autowired`等注解配合，降低代码耦合度。
    -   **Bean的作用域**：**`singleton`** (默认，单例)、**`prototype`** (每次获取创建新实例)、`request`、`session`。
    -   **解决循环依赖**：Spring通过**三级缓存**解决`singleton`作用域下的循环依赖问题。
-   **Spring AOP (面向切面编程)**：将日志记录、事务管理、权限检查等**横切关注点**与业务逻辑分离，提高模块化。依赖于**动态代理**机制。
-   **Spring 事务管理**：
    -   **声明式事务**：通过 `@Transactional` 注解即可实现，是主流方式。其核心是AOP。
    -   **事务失效场景**：`private`/`final`方法、**同类内部方法调用**（绕过代理对象）、异常类型不满足回滚条件（默认只回滚`RuntimeException`）等。
-   **Spring Cloud 微服务**：
    -   **核心组件**：**服务注册与发现 (Eureka/Nacos)**、**远程调用 (Feign)**、**负载均衡 (Ribbon)**、**断路器 (Hystrix/Sentinel)**、**API网关 (Zuul/Gateway)**。
    -   **分布式事务**：微服务架构中的难点。常见方案包括：**二阶段提交 (2PC)**、**TCC**、**可靠消息最终一致性** (如RocketMQ事务消息)。

### 6. 分布式系统与中间件

构建高可用、高并发的系统离不开分布式理论和优秀的中间件。

-   **分布式理论**：
    -   **CAP理论**：分布式系统在**一致性 (C)**、**可用性 (A)**、**分区容错性 (P)** 之间只能三选二。网络分区是必然的，因此架构设计通常在**CP** (如ZooKeeper) 和**AP** (如Eureka) 之间选择。
    -   **BASE理论**：对AP模式的扩展。核心思想是**基本可用 (BA)**、**软状态 (S)** 和**最终一致性 (E)**。
-   **缓存 (Redis)**：
    -   **数据结构**：支持`String`、`Hash`、`List`、`Set`、`ZSet`等丰富结构。
    -   **持久化**：**RDB** (快照) 和 **AOF** (追加日志)。两者结合使用可达到较好的数据安全性。
    -   **集群方案**：**主从复制**、**哨兵 (Sentinel)** 模式、**Redis Cluster**。
    -   **经典问题**：**缓存穿透**、**缓存击穿**、**缓存雪崩**，以及**缓存与数据库双写一致性**（如Cache Aside Pattern）。
-   **消息队列 (Kafka)**：
    -   **核心概念**：**Producer**, **Consumer**, **Topic**, **Partition**, **Broker**, **Offset**。
    -   **高吞吐量**：依赖**顺序写入磁盘**、**零拷贝**、**批量发送**等技术。
    -   **消息可靠性**：Producer端ACKS设置、Broker端副本机制、Consumer端手动提交Offset。
    -   **Exactly Once 语义**：在Kafka 0.11+ 版本，通过**幂等性**和**事务**实现。
